1. Project Overview & Objectives

Purpose: This document provides a complete, context-ready implementation
blueprint for a Python-based algorithmic trading system designed to pass
the Topstep $50,000 Trading Combine. It is written for a developer with
Python proficiency but who may not have prior financial markets or
quantitative finance experience.

Core Design Philosophy: The challenge is not a return-maximization
problem — it is a constrained survival problem. The system must reach a
$3,000 profit target without breaching a $2,000 Maximum Loss Limit
(MLL). Every architectural decision flows from this constraint.

4. Module 1: Monte Carlo Validator (Build First)

Build this module before any live-execution code. It validates that the
chosen risk parameters (win rate, risk:reward, position size) can
survive the $2,000 MLL constraint with high probability. It has zero API
dependencies and can run immediately.

4.1 What It Does

The Monte Carlo engine takes a distribution of historical or
hypothetical trade results, randomizes the sequence 10,000 times, and
measures how often the simulated account touches the $2,000 MLL before
reaching the $3,000 profit target. This surfaces sequence risk that
standard chronological backtesting cannot reveal.

4.2 Required Inputs

  ---------------------------------------------------------------------------
  Input              Type          Description
  ------------------ ------------- ------------------------------------------
  win_rate           float         Historical or assumed win rate (e.g., 0.55
                     (0.0–1.0)     for 55%)

  avg_win            float (USD)   Average winning trade P&L in dollars
                                   (e.g., $30)

  avg_loss           float (USD)   Average losing trade P&L as negative value
                                   (e.g., -$22)

  starting_capital   float (USD)   Starting value = MAX_LOSS_LIMIT = $2,000

  ruin_boundary      float (USD)   Lower boundary = 0 (account fully at MLL =
                                   bust)

  target_boundary    float (USD)   Upper boundary = PROFIT_TARGET = $3,000
                                   above start

  n_simulations      int           Number of Monte Carlo runs (minimum
                                   10,000)

  max_trades         int           Max trades per simulation before declaring
                                   inconclusive
  ---------------------------------------------------------------------------

4.3 Implementation Logic

  # risk/monte_carlo.py — simplified pseudocode

  import numpy as np

  from config import MAX_LOSS_LIMIT, PROFIT_TARGET, MC_SIMULATIONS,
  MC_MAX_TRADES

  def run_simulation(win_rate, avg_win, avg_loss, n_sim=MC_SIMULATIONS):

  ruin_count = 0

  target_count = 0

  max_dd_list = []

  longest_streak_list = []

  for _ in range(n_sim):

  capital = MAX_LOSS_LIMIT # $2,000 starting true capital

  peak = capital

  max_dd = 0

  streak = 0

  max_streak = 0

  for _ in range(MC_MAX_TRADES):

  outcome = avg_win if np.random.random() < win_rate else avg_loss

  capital += outcome

  # Track peak and drawdown

  if capital > peak:

  peak = capital

  dd = peak - capital

  if dd > max_dd:

  max_dd = dd

  # Track losing streaks

  if outcome < 0:

  streak += 1

  max_streak = max(max_streak, streak)

  else:

  streak = 0

  # Check boundary conditions

  if capital <= 0: # Hit MLL (ruin)

  ruin_count += 1

  break

  if capital >= MAX_LOSS_LIMIT + PROFIT_TARGET: # Hit target

  target_count += 1

  break

  max_dd_list.append(max_dd)

  longest_streak_list.append(max_streak)

  return {

  'ruin_probability': ruin_count / n_sim,

  'target_probability': target_count / n_sim,

  'max_drawdown_p95': np.percentile(max_dd_list, 95),

  'max_losing_streak_p95': np.percentile(longest_streak_list, 95),

  }

5. Module 2: HMM Regime Classifier

The Hidden Markov Model determines which market regime is active for the
following trading session. It runs each evening after market close,
takes observable market data as input, and outputs one of three states
that controls which strategy fires the next day.

5.1 The Three States

  ----------------------------------------------------------------------------
  State   Label             Condition                Strategy Activated
  ------- ----------------- ------------------------ -------------------------
  State 0 Balanced /        Ranging, low ATR, VIX    Strategy A: VWAP Mean
          Low-Volatility    term structure flat or   Reversion
                            backwardated             

  State 1 Directional /     Trending, elevated ATR,  Strategy B: 15-Min ORB
          High-Volatility   VIX in contango          Breakout

  State 2 Extreme Stress /  VIX spike, abnormal      No trading — cash
          Crisis            realized vol, black swan preservation
                            indicators               
  ----------------------------------------------------------------------------

5.2 Feature Inputs

The HMM is trained on three observable daily features per bar. All
features must be computable from data available before the next session
opens (no lookahead):

-   Daily Log Return: log(close_t / close_t-1). Captures directional
      bias.

-   Realized Volatility (ATR Percentile): The 14-day ATR expressed as a
      percentile rank over the past 252 days. Values above 80th
      percentile indicate a high-vol regime.

-   VIX Term Structure Slope: (VIX3M - VIX) / VIX, where VIX3M is the
      3-month VIX. A positive slope (contango) indicates calm; a
      negative slope (backwardation) indicates stress or trending
      regime.

5.3 Critical: Walk-Forward Validation

This is the most important implementation constraint for the HMM.
Fitting the model on the full historical dataset simultaneously creates
lookahead bias — the model will appear to predict regimes it actually
learned from future data. This completely invalidates live performance.

  Walk-Forward Implementation Rule

  The HMM must ONLY be trained on data available up to day t to predict
  the regime for day t+1.

  Use an expanding window: start with 504 days of history
  (HMM_LOOKBACK_DAYS), then add one day at a time.

  Never use a sliding window — expanding window preserves the growing
  information set as in live trading.

  Refit runs autonomously at NIGHTLY_REFIT_TIME (17:30 CT) after each
  session close.

5.4 Implementation Outline

  # regime/hmm_classifier.py — simplified pseudocode

  from hmmlearn.hmm import GaussianHMM

  import numpy as np

  import pandas as pd

  from config import HMM_N_STATES, HMM_LOOKBACK_DAYS,
  HMM_COVARIANCE_TYPE, HMM_N_ITER

  class RegimeClassifier:

  def __init__(self):

  self.model = None

  self.state_map = {} # Maps HMM state int -> RegimeState enum

  def fit(self, feature_df: pd.DataFrame):

  '''

  feature_df columns: ['log_return', 'atr_percentile', 'vix_term_slope']

  Only pass data available up to and including yesterday.

  '''

  X = feature_df[['log_return', 'atr_percentile',
  'vix_term_slope']].values

  X = X[-HMM_LOOKBACK_DAYS:] # Use only the lookback window

  self.model = GaussianHMM(

  n_components=HMM_N_STATES,

  covariance_type=HMM_COVARIANCE_TYPE,

  n_iter=HMM_N_ITER

  )

  self.model.fit(X)

  self._map_states_to_regimes(X)

  def predict_next_regime(self, feature_df: pd.DataFrame) -> int:

  '''Returns predicted state (0, 1, or 2) for the next session.'''

  X = feature_df[['log_return', 'atr_percentile',
  'vix_term_slope']].values

  X = X[-HMM_LOOKBACK_DAYS:]

  hidden_states = self.model.predict(X)

  return int(self.state_map.get(hidden_states[-1], 0))

  def _map_states_to_regimes(self, X):

  '''

  HMM states are arbitrarily numbered — must map to economic meaning.

  Sort by mean realized volatility: lowest vol = State 0, highest =
  State 2.

  '''

  means = self.model.means_

  atr_col_idx = 1 # atr_percentile is second column

  vol_order = np.argsort([m[atr_col_idx] for m in means])

  self.state_map = {vol_order[0]: 0, vol_order[1]: 1, vol_order[2]: 2}

6. Module 3: Strategy Engine

6.1 Strategy A — VWAP Mean Reversion (State 0)

Activation condition: HMM outputs State 0 (balanced, low-volatility
regime) for the session.

VWAP (Volume-Weighted Average Price) is the institutional equilibrium
price for the session. When price deviates significantly from VWAP,
institutional algorithms tend to push it back. This strategy fades those
extremes.

6.1.1 Entry Logic

6.  Compute VWAP and Standard Deviation Bands: Calculate anchored VWAP
    and rolling SD bands from the Regular Trading Hours (RTH) open (9:30
    ET). Compute ±2.5σ and ±3.0σ bands continuously every bar.

7.  Entry Gate: The algorithm only arms itself when price reaches the
    ±2.5σ to ±3.0σ band. Price touching inside 2.5σ does not qualify.

8.  CVD Divergence Confirmation (mandatory): At the price extreme, check
    Cumulative Volume Delta (CVD). If price makes a lower low but CVD
    makes a higher low (bullish divergence at the lower band), the
    institutional absorption signal is confirmed. If no divergence, no
    trade.

9.  Execution: Market order (or tight limit) in the mean-reversion
    direction. Target is the VWAP centerline.

6.1.2 Exit Logic

-   Profit Target: VWAP baseline (the center band, not a fixed point
      target)

-   Stop Loss: 1.5 × 5-minute ATR beyond the entry extreme. If entered
      at -2.5σ, stop is placed 1.5× ATR below -2.5σ.

-   Time Stop: Any open position at 3:05 PM CT is closed regardless of
      P&L.

-   Daily trade cap: Maximum 3 VWAP trade attempts per session.

6.1.3 CVD Implementation Detail

CVD is the cumulative sum of (bid volume - ask volume) over the session.
It requires tick-level data classified as bid-initiated or
ask-initiated. This is the technically hardest indicator to implement:

  # data/indicators.py — CVD pseudocode

  class CVDCalculator:

  def __init__(self):

  self.cumulative_delta = 0.0

  self.bar_deltas = [] # CVD value at end of each bar

  def on_tick(self, price, size, side): # side: 'buy' or 'sell'

  if side == 'buy':

  self.cumulative_delta += size

  else:

  self.cumulative_delta -= size

  def close_bar(self):

  self.bar_deltas.append(self.cumulative_delta)

  def detect_divergence(self, price_bars, lookback=3):

  '''

  Bearish divergence: price higher high + CVD lower high (at upper band)

  Bullish divergence: price lower low + CVD higher low (at lower band)

  '''

  if len(price_bars) < lookback or len(self.bar_deltas) < lookback:

  return None

  price_recent = price_bars[-lookback:]

  cvd_recent = self.bar_deltas[-lookback:]

  price_dir = price_recent[-1] - price_recent[0]

  cvd_dir = cvd_recent[-1] - cvd_recent[0]

  if price_dir < 0 and cvd_dir > 0: return 'BULLISH'

  if price_dir > 0 and cvd_dir < 0: return 'BEARISH'

  return None

6.2 Strategy B — 15-Minute Opening Range Breakout (State 1)

Activation condition: HMM outputs State 1 (directional, high-volatility
regime) for the session.

6.2.1 Entry Logic

10. Define the Opening Range: Record the absolute high and absolute low
    of the first 15 minutes of the RTH session (9:30–9:45 ET). This is
    the ORB range.

11. Breakout Detection: Monitor for the first 5-minute candle that
    closes completely outside the ORB boundary (above the high for a
    long, below the low for a short). A close is required — not just a
    wick breach.

12. Entry: Enter market order in the direction of the breakout on the
    candle close.

6.2.2 Exit Logic

-   Stop Loss: Placed at the midline of the ORB range (or the opposite
      side of the range for wider ranges). This is a structural stop.

-   Profit Target: 1:1.5 risk-to-reward. If stop distance is 10 ticks,
      target is 15 ticks in the breakout direction.

-   Daily trade cap: Maximum 2 ORB attempts per session. If both fail,
      trading halts for the day.

-   Time Stop: All positions closed at 3:05 PM CT.

  ------------------------------------------------------------------------
  Parameter          Value                 Rationale
  ------------------ --------------------- -------------------------------
  Opening Range      9:30–9:45 ET (15 min) Captures initial institutional
  Window                                   order flow consensus

  Breakout           Full candle close     Prevents false breakout entries
  Confirmation       outside range         on wicks

  Stop Location      ORB midline or        Structural stop; defines the
                     opposite side         range invalidation point

  Risk:Reward        1:1.5 minimum         Ensures positive expectancy
                                           even at 40% win rate

  Max Daily Trades   2                     Prevents chop-induced drawdown
                                           on indecisive days
  ------------------------------------------------------------------------

7.3 Order Manager Flow

Every trade execution follows this exact sequence with no exceptions:

13. Pre-trade check: Call circuit_breakers.check_all() — reject
    immediately if any breaker is active.

14. Size calculation: Call position_sizer.calculate() — returns MES
    contract quantity (almost always 1 contract given $20-40 risk per
    trade).

15. Order placement: Call api_client.place_order() with the sized
    quantity.

16. Confirm fill: Poll or receive WebSocket fill confirmation. If no
    fill in 30 seconds, cancel and log.

17. Set exit orders: Immediately place stop-loss and profit-target
    orders as OCO (one-cancels-other) if supported, or manage manually
    via WebSocket monitoring.

18. Update P&L tracker: Increment daily_pnl and trade_count in the
    session state object.

19. Log trade: Write full trade record to logs/ with timestamp, regime
    state, entry, exits, and P&L.

8. Module 5: Session Manager

The session_manager.py is the top-level orchestrator. It ties all
modules together and manages the daily lifecycle using APScheduler for
timed events.

  -------------------------------------------------------------------------

  ------------- ------------------ ----------------------------------------

  eve)                             HMM; save tomorrow's regime state to

  08:30         Pre-Market Init    Load regime state; initialize circuit
                                   breakers; connect WebSocket; verify API

                                   arm ORB timer (Strategy B) per regime

  09:30–09:45   ORB Window         If State 1: record every tick for

                                   allowed yet

8.2 State Persistence

The session manager must persist the following state across restarts
(write to a JSON file after every update):

-   cumulative_pnl: Total realized P&L since challenge start — needed
      for consistency rule calculation

-   daily_pnl: Today's realized P&L — reset to 0.0 at session open

-   daily_trade_count: Number of trades today — compared against
      strategy trade cap

-   current_regime: HMM output for today (0, 1, or 2)

-   account_high_water_mark: Highest realized balance achieved — used to
      calculate MLL trailing threshold

-   challenge_status: IN_PROGRESS, PASSED, or FAILED — once FAILED, all
      trading must halt

  EOD Close Logic    Positions always flattened before 3:05 PM CT even if
                     circuit breaker was triggered earlier

9.2 Integration Testing

Before connecting to a live ProjectX account, run a complete
paper-trading simulation locally:

20. Replay mode: Feed recorded tick data from a recent trading session
    through the full strategy engine and verify circuit breakers trigger
    at correct P&L levels.

21. Regime switching test: Force-set the regime to each state (0, 1, 2)
    and verify the correct strategy activates or trading halts.

22. EOD stress test: Simulate a trade still open at 3:04 PM CT and
    verify it is forcibly closed at 3:05 PM CT.

23. API error handling: Simulate HTTP 429, 503, and network timeout
    errors and verify the system does not place duplicate orders or get
    stuck.
